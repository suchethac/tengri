# Float32 Tier A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current float32 path's "cast back to float64 for distance
scaling" crutch with a genuine log-offset reparametrization of the multiplicative
scale seams (flux projection, ionizing-SED mass scale), so the forward model is
correct in *pure* float32 while remaining machine-precision-identical in float64.

**Architecture:** A small pure helper (`utils/scale.py`) carries large physical
scale factors as `log10` offsets and applies them to a peak-normalized array, so
no out-of-range intermediate (`d_L²`≈4e56, `flux_scale`≈1e-58, `mass_scale`≈1e42)
is ever materialized. Every existing `flux_scale = (1+z)/(4π d_L²)` site routes
through this helper. A golden-reference parity harness pins current-main f64
outputs so each change is proven to leave f64 unchanged (rtol ≤ 1e-12) and to
make pure-f32 finite and accurate (rtol ≤ 1e-3).

**Tech Stack:** JAX (jax.numpy), pytest, chex, numpy. No new dependencies.

## Global Constraints

- **"Exact under f64" = rtol ≤ 1e-12 vs the pre-change reference, NOT bit-identical.**
  A reparametrization reorders floating-point operations, which changes rounding
  by ≤ a few ULP. 1e-12 is ~1e4× tighter than any science or regression
  tolerance in this repo, so no existing test moves. Literal bit-exactness is not
  achievable alongside a reparametrization and is a non-goal.
- **"Correct under f32" = rtol ≤ 1e-3 vs the f64 reference**, finite everywhere,
  across the z ∈ {0.01, 0.1, 0.5, 1, 3, 6} × log₁₀M ∈ {8, 10, 11} grid the
  feasibility study (#1186) showed is *universally* affected.
- **Scope = forward model + projection only.** Inference/gradients under f32 and
  the energy-balance *reduction* reformulation are Tier B and explicitly out of
  scope here. Precompute (`*_precompute.py` numpy build-time tables) stays
  float64 on the host per the memo.
- **Units** (repo rule): years, Ångström, Msun/yr, erg/s/Hz for L_ν. American
  English. Line length 99. Numpydoc docstrings with units in brackets and JIT
  flag in Notes.
- **Naming contract**: `SEDModel`, `Parameters`, etc. Read
  `docs/dev/NAMING_CONTRACT.md` before any rename.
- **Reference the feasibility study**: issue #1186 (verdict + measured evidence).

```python
def build_model(ssp, forward_dtype):
    from tengri import SEDModel, recipes
    from tengri.observation import Observation, Photometry
    obs = Observation(photometry=Photometry.from_names(
        ["galex_fuv", "sdss_r", "wise_w1", "wise_w4", "herschel_250"]))

    recipe["approx"] = None
    return SEDModel.build(ssp_data=ssp, observation=obs,
                          forward_dtype=forward_dtype, **recipe)


def forward_outputs(model, z, log10_mass):
    p = dict(model.spec.sample(jax.random.PRNGKey(0)))
    p["redshift"] = z
    p["sfh_dpl_log_total_mass"] = log10_mass
    pred = model.predict(p)
    return {
        "photometry": np.asarray(pred.photometry(), dtype=np.float64),
        "rest_sed": np.asarray(pred.rest_sed(), dtype=np.float64),
        "halpha": np.float64(pred.lines.halpha),
        "l_tir": np.float64(pred.properties["l_tir"]),
        "q_h": np.float64(pred.properties["q_h"]),
    }
```

```python
# src/tengri/utils/scale.py
# SPDX-License-Identifier: BSD-3-Clause
"""Range-safe application of large log10 scale factors (float32 feasibility).

Physical scales in this code (``mass_scale`` ~ 1e42 erg/s, ``d_L²`` ~ 1e56 cm²,
``flux_scale`` ~ 1e-58) fall outside the float32 window ``[1.18e-38, 3.40e38]``.
This module applies such a scale to an array by carrying it as a ``log10``
offset and peak-normalizing the array, so no out-of-range intermediate is
materialized. In float64 the result equals the naive product to machine
precision; in float32 it stays finite whenever the *net* magnitude is in range.
See issue #1186.
"""
from __future__ import annotations

import jax.numpy as jnp

LN10 = 2.302585092994046
LOG10_4PI = float(jnp.log10(4.0 * jnp.pi))  # ~1.09921


def pow10(x):
    """10**x, computed as ``exp(x·ln10)`` to preserve the input dtype.

    Parameters
    ----------
    x : array_like
        Exponent [dimensionless].

    Returns
    -------
    ndarray
        ``10**x`` in the dtype of ``x``.

    Notes
    -----
    JIT/grad/vmap-safe. ``jnp.power(10.0, x)`` would promote to float64 under
    weak typing; ``exp(x·ln10)`` does not.
    """
    return jnp.exp(x * LN10)


def apply_log10_scale(arr, log10_scale):
    """Return ``arr * 10**log10_scale`` without out-of-range intermediates.

    Parameters
    ----------
    arr : array_like
        Values to scale (any magnitude within the dtype range).
    log10_scale : array_like, scalar
        Base-10 log of the multiplicative factor [dimensionless]. May be far
        outside the dtype range (e.g. -58); only the *net* result must be
        representable.

    Returns
    -------
    ndarray
        ``arr * 10**log10_scale``, equal to the naive product within ~1e-12 in
        float64 and finite in float32 when ``max|arr| * 10**log10_scale`` lies in
        the dtype's normal range.

    Notes
    -----
    JIT/grad/vmap-safe. Factors ``arr`` by its peak so the exponentiated scale
    is applied to an O(1) array; the peak's decades are folded into the exponent.
    """
    peak = jnp.max(jnp.abs(arr))
    peak = jnp.where(peak > 0, peak, jnp.ones_like(peak))
    net = log10_scale + jnp.log10(peak)
    return (arr / peak) * pow10(net)
```
